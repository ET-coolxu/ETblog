## 前置约束

- 先澄清假设，不臆造需求
- 改动范围最小化
- 遵循 `.cursor/rules`；产品行为以用户本次说的「现在开始做 V…」为准，文档在 `docs/requirements/`，没说明时先问。结构以 `docs/架构/项目架构.md` 为准
- 用户可见文案用简体中文
- 用户可见日期跟站内已有的日期格式函数（本仓库是 `formatPostDate`）。若一边给了日期示例、一边又要求用该函数，写死用哪一种；不要把示例里的 ISO 日期（如 `2026-11-01`）当成正式文案
- 后台表单在 Server Action 结束后会重置非受控文本框。要求保存失败仍留下刚输入的内容时，用受控输入
- 范围变化时，按 `.cursor/rules/iteration.mdc` 同步规则、架构说明和 README
- 当前需求写明「本期不做」的能力不要实现
- Markdown 是唯一信源：`content/posts/{slug}.md`、`content/pages/about.md`。不另存文章数据库
- 只被少数页面用到、又会把 Markdown 编译器拖进公共模块的函数，按需 import，避免文章列表、发文接口等热路径静态打包带上编译器
- slug 仅 `[a-z0-9-]+`，创建后不可改；读写防路径穿越
- 图片放在 `public/uploads/{yyyy}/{mm}/`。发布后 `revalidatePath`，不整站重建
- sitemap 若只说「加上路径」，`changeFrequency` 与 `priority` 沿用相邻静态页；没有单独要求就不要另造优先级
- 站名和作者来自 `getSiteConfig()`，不写死
- 单管理员 session；搜索用服务端 Flexsearch；统计用应用内 SQLite
- 功能先合入 `test` 看构建，再生产只跟 `main` 的 GHCR 镜像

## 工作流程

1. 阅读当前需求文档、架构说明和相关规则，列出本次会改的文件
2. 信息不够时先追问，不靠猜测补需求
3. 若本次范围超出当前需求文档，先更新 `docs/requirements/`，再按迭代规则更新规则和说明，然后写代码
4. 实现后对照需求里的验收项自查
5. 若可沉淀通用经验，回复末尾用「提示词库建议」提出，确认后再改 `docs/agent/` 的类型模板
