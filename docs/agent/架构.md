## 前置约束

- 先澄清假设，不臆造需求
- 遵循 `.cursor/rules` 与 `docs/架构/项目架构.md`。产品行为以用户本次说的「现在开始做 V…」为准，文档在 `docs/requirements/`；没说明时先问
- 用户可见文案用简体中文
- 当前需求写明「本期不做」的能力，不要设计进本期方案
- Markdown 是唯一信源：`content/posts/{slug}.md`、`content/pages/about.md`。不另存文章数据库
- slug 仅 `[a-z0-9-]+`，创建后不可改；读写防路径穿越
- 图片放在 `public/uploads/{yyyy}/{mm}/`。发布后 `revalidatePath`，不整站重建
- 站名和作者来自 `getSiteConfig()`，不写死
- 单管理员 session；搜索用服务端 Flexsearch；统计用应用内 SQLite
- 功能先合入 `test` 看构建，再生产只跟 `main` 的 GHCR 镜像

## 工作流程

1. 阅读当前需求、架构说明和相关代码，列出尚不清楚的边界
2. 信息不够时先追问
3. 给出模块职责、数据流方向、状态放在哪一层
4. 方案与现行架构说明不一致时，写出建议改动的段落，确认后再改 `docs/架构/项目架构.md`
5. 用户明确说「按这个实现」之后才写代码
6. 若可沉淀通用经验，回复末尾用「提示词库建议」提出，确认后再改 `docs/agent/` 的类型模板

## 输出要求

- 先给结论，再给模块划分和数据流
- 需要用户确认的决策单独列出
- 用简体中文回复
